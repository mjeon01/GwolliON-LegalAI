# 권리ON — 전문기 AI 기능 구현 가이드

> [!abstract] 먼저 판단할 내용
> 전문기가 만들 핵심은 **계약조건 추출 → 주의할 조항 탐지 → 관련 근거 검색 → 쉬운 설명 → 추가 질문·다음 행동·문서 초안**을 연결하는 AI 처리 모듈이다.
> 서비스는 먼저 기존 LLM으로 전체 흐름을 만들고, 별도로 소형 모델을 LoRA 학습하여 같은 평가셋에서 비교한다. 개선이 확인된 학습 모델을 해당 단계에 교체 적용하는 구성을 제안한다.

## 이 문서의 기준

- `plan.hwp`의 전문기 담당 활동을 읽고 구현 작업으로 변환했다.
- 원문에 있는 요구사항과 이 문서에서 제안하는 기술·수량·성능 목표를 구분했다. **제안값은 확정 요구사항이나 측정 결과가 아니다.**
- 가이드 작성 당시에는 계획서와 초기 Obsidian 보관함이 있었다. 아래의 AI 서비스 모듈·API·코드 경로는 앞으로 구현할 설계다.
- 2026-10-10에는 다운로드 데이터와 법령 API를 실제 점검했고, 재실행할 점검 스크립트를 추가했다. 결과는 [[09 실제 데이터와 법령 API 점검]]에 있다.
- 같은 날 로컬 웹 화면·분석 API·추가 질문·초안·다국어 안내를 연결한 1차 MVP를 구현했다. 현재 실행·검증 상태와 미구현 범위는 [[10 1차 MVP 실행과 검증]]에 있다. 아래 설계 전체가 구현된 것은 아니다.
- 원문의 활동보고서에 적힌 학습·구축 활동의 실제 수행 여부는 이 저장소만으로 확인하지 않았다.
- 법령 내용 자체를 확정하는 문서가 아니라, 근거를 조회하고 검증하는 기능의 구현 문서다.

## 추천하는 기능 범위

| 단계 | 사용자가 할 수 있는 일 | 전문기가 구현할 부분 | 완료를 판단할 증거 |
| --- | --- | --- | --- |
| P0: 근로계약 핵심 흐름 | 임금·근로시간·기간 등을 확인하고 원문으로 돌아가기 | 구조화 추출, 조항 후보 탐지, 근거 검색, 한국어 설명 | 계약서별 정답과 비교한 결과, 원문 하이라이트 |
| P0: 학습 실험 | 학습 전후 모델의 차이 확인 | 데이터 변환, 1차 LoRA, 오류 분석, 2차 개선 | adapter, 데이터 버전, 동일 평가셋 비교표 |
| P1: 권익구제 흐름 | 부족한 정보를 답하고 다음 행동을 확인하기 | 추가 질문, 증빙 체크리스트, 사실확인 요청문 초안 | 시나리오 입력부터 초안까지의 실행 기록 |
| P1: 임대차 시나리오 | 보증금·기간·특약을 확인하고 확인할 자료 파악하기 | 임대차 추출 스키마, 제한된 쟁점 묶음, 근거 연결 | 청년 임차인·피해 의심 시나리오 테스트 |
| P1: 다국어 연결 | 같은 분석 결과를 중국어·스페인어로 읽기 | 한국어 결과와 숫자·근거 ID를 유지한 번역 인터페이스 | 담당자 용어 검수, 금액·날짜 일치 검사 |
| P2: 확장 | 여러 증빙을 종합하고 복잡한 문서 작성하기 | 증빙 교차 검증, 더 많은 계약유형, 고급 초안 | P0/P1 평가를 통과한 뒤 범위 결정 |

원문은 전세사기 피해자·외국인 근로자·사회초년생의 세 시나리오를 요구한다. **구현은 근로계약부터 시작하되, 11주차 시연과 13주차 최종 테스트에는 제한된 임대차 흐름도 포함**한다. 임대차 흐름은 계약서·사용자 진술로 확인 가능한 항목과 추가 증빙을 구분한다.

## 노트 읽는 순서

**현재 실행 상태는 [[10 1차 MVP 실행과 검증]], 실제 데이터는 [[09 실제 데이터와 법령 API 점검]]부터 확인한다.** 아래 노트는 전체 설계와 비교 기준이다.

1. [[01 전체 아키텍처]] — 서비스·학습 구조, 실행 순서, 추천 기술.
2. [[02 기능별 구현 프로세스]] — 각 기능의 입력·처리·출력·실패 대응.
3. [[03 데이터와 법률 RAG]] — 실제 데이터 후보, 라벨 설계, 근거 검색.
4. [[04 모델 학습과 기술 선택]] — API·로컬 모델 비교, LoRA 실험 방법.
5. [[05 API와 팀 연동]] — OCR·보안·앱·번역 담당자와 주고받을 데이터.
6. [[06 평가와 완료 기준]] — 정량 평가, 오류 분석, 최종 시나리오.
7. [[07 주차별 작업과 결정표]] — 원문 활동 매핑, 남은 일정, 선택 체크리스트.
8. [[08 근거와 공식 문서]] — 확인한 공식 자료와 확인 범위.
9. [[09 실제 데이터와 법령 API 점검]] — 받은 데이터 수량·실제 스키마·법령 조회 결과.
10. [[10 1차 MVP 실행과 검증]] — 로컬 화면·샘플·실제 Qwen 추출·검증 결과·현재 한계.

빠르게 검토하려면 **아키텍처 → 기능 프로세스 → 주차별 결정표** 순서로 먼저 읽으면 된다.

> [!tip] 도식 보는 방법
> 아키텍처와 처리 흐름은 Obsidian의 Mermaid 코드 블록으로 넣었다. 노트를 **읽기 보기**로 전환하면 도식으로 볼 수 있다. 코드가 보이는 소스 모드에서는 읽기 보기로 전환한다. [Obsidian 공식 도식 안내](https://help.obsidian.md/Editing+and+formatting/Advanced+formatting+syntax)

## 왜 이 구조인가

| 기술 | 맡기는 역할 | 구현에서 확인할 것 |
| --- | --- | --- |
| LLM | 문장의 의미 이해, 항목 추출, 쉬운 설명 | JSON 형식, 원문 일치, 누락·추측 여부 |
| 규칙 | 단위 정규화, 필수 입력 확인, 숫자 계산 | 적용 조건과 시행일, 계산식, 경계값 |
| RAG | 관련 법령·공식 안내를 찾아 설명에 전달 | 검색된 근거의 내용·시점·적용 조건 |
| LoRA 학습 | 계약서 항목 추출과 분류 행동 개선 | 같은 모델의 학습 전후 비교 |
| AI Agent | 분석 결과에 따라 질문·검색·초안을 연결 | 분기별 상태, 도구 입력, 재시도·종료 조건 |

최신 법령은 검색 데이터로 관리하고, 파인튜닝은 **원문에서 사실을 잘 뽑는 능력과 정해진 형식으로 답하는 능력**에 집중한다. 초기 Agent는 Python의 명시적인 상태 흐름으로 구현한다.

## 사용자에게 보일 결과 예시

가상의 근로계약서를 올리면 아래처럼 보여준다.

```text
월 급여: 2,500,000원
원문: "월급은 250만원으로 한다." / 1페이지 / B001

확인할 항목: 지급일
현재 문서에서 지급일을 확인하지 못했습니다.
누락된 페이지가 있는지 먼저 확인해주세요.

추가 질문: 주당 근무시간과 사업장 규모를 확인할 수 있나요?
다음 행동: 계약서, 급여명세서, 근무기록 준비
문서 초안: 확인된 사실을 넣은 근로조건 확인 요청문
```

여기서 원문 확인과 법률 판단은 각각 검증한다. 일부 항목을 찾지 못하면 분석 범위와 미확인 정보를 함께 표시한다.

## 내가 결정할 항목

- [ ] 서비스 기준 모델을 API로 시작할지, 로컬 모델로 시작할지 결정한다.
- [ ] 근로계약 P0의 추출 항목과 쟁점 5~8종을 확정한다.
- [ ] 지도교수 또는 검토자가 라벨·법률 근거를 확인할 시간을 확보한다.
- [ ] 학습 환경을 Apple Silicon MLX 또는 NVIDIA GPU TRL 중 하나로 정한다.
- [ ] 임대차 P1의 범위를 보증금·기간·반환 관련 특약 등으로 제한한다.
- [ ] API 전송이 가능한 비식별 입력 범위를 김유나와 합의한다.

세부 선택의 장단점은 [[04 모델 학습과 기술 선택]], 실제 주차별 실행 순서는 [[07 주차별 작업과 결정표]]에서 확인한다.
